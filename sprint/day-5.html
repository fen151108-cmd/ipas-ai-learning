生成式 AI 系統整合：RAG、代理協作與語音工作流

RAG 找證據，微調改行為，Planner 排步驟，MCP 接工具，A2A 讓代理協作；端到端先守品質與權限，再優化速度。

今天為什麼要學？

7 天衝刺第 5 天，從單一模型走向可營運系統；建議 50–60 分鐘，先分知識、行為、規劃、工具與代理，再用完整服務助手及跨產業案例演練。

  • 能判斷 RAG、Fine-tuning、API、Planner、MCP 與 A2A 各解決哪一層問題。
  • 能畫出 ASR→LLM／RAG→API→輸出的服務助手鏈，並標出權限、引用與人工確認點。
  • 能區分會議說話者、主題邊界、語意分群與批次吞吐／單請求延遲。

一、8 分鐘框架：把系統拆成知識、推理、工具、代理與輸出

生成式 AI 應用不是只換一個更大的模型。完整系統通常包含輸入辨識、外部知識、模型推理、工作規劃、工具執行、代理協作、輸出與監控。看到題目先判斷問題發生在哪一層，才不會把所有需求都回答成微調或代理。

今天採「先品質、後速度」：先確認語音辨識是否可靠、檢索是否命中、引用是否支持答案、動作是否授權，再談快取、平行化或批次。若快速產生錯答案或越權動作，延遲再低也不是成功。

  • 主線：輸入 → 知識／推理 → 規劃 → 工具／代理 → 輸出 → 監控。
  • 先定驗收：正確、忠實、權限、可追溯、動作成功，再加速度與成本。

二、RAG 與 Fine-tuning：更新知識和調整行為不是同一件事

RAG 在回答時先從外部知識庫檢索片段，再把問題與證據交給模型。它適合常更新、需要引用與版本追蹤的規範，但必須在檢索前做身分與資料權限過濾，不能先取出機密內容再期待模型自行隱藏。答案要保留來源、版本與無證據時的拒答或轉人工。

Fine-tuning 會用資料更新模型參數，常用於穩定格式、語氣或特定任務行為；但它不是達成一致語氣的唯一手段。先比較系統提示、模板、結構化輸出、範例與後處理，若長期仍不穩且有足夠高品質資料，再評估微調。頻繁更新事實與逐答引用通常更偏 RAG。

  • RAG：外部知識可更新、可引用；仍要驗證檢索與生成忠實度。
  • 微調：改參數與行為；不等於即時知道最新文件。
  • 權限過濾應在檢索與回傳階段都落實。

三、API、Planner、MCP、A2A：動作、規劃、工具協定與代理協作

API 依明確介面送參數、執行查詢或改變外部狀態；它負責「做動作」，不等於自己規劃。Planner 根據目標拆解步驟、安排順序、選工具並依結果調整；高風險動作仍須權限、參數驗證、冪等、人工確認與回退。

MCP 用共同協定描述與連接工具、資源或提示，重點是 AI 應用與工具的標準化介面；A2A 則偏代理與代理之間的能力發現、任務委派及狀態交換。典型 A2A 由 Client Agent 發起請求，Remote Agent 接受並回應；短任務可同步回傳，長任務也可非同步處理、更新狀態後再交付結果。

  • API 做；Planner 想步驟；MCP 接工具；A2A 接代理。
  • 非同步表示不用阻塞等完整結果，不表示任務沒有狀態與失敗處理。

付款重試：冪等與狀態查核

付款逾時不表示交易未完成。先查交易狀態；若需要重試，同一筆交易應沿用相同冪等鍵，且API工具端必須支援辨識重複請求並回傳既有結果，避免重複扣款。狀態仍不明時暫停自動重送並轉人工；不能每次重試都產生新鍵，也不能只靠提示要求模型不要重複。

四、完整服務助手：ASR 到引用、動作與輸出

中性服務助手收到語音詢問後，先由 ASR 轉成文字並標記低信心片段；LLM 判斷意圖，RAG 依使用者權限檢索最新版規範與引用；若只是問答就依證據生成，若要查進度或建立申請，Planner 先列步驟，再透過受控 API 執行，必要時由 A2A 委派專門代理。

輸出前要核對人、時間、數字、引用與動作結果；會改資料、送出申請或產生成本的操作，先向使用者展示關鍵參數並取得確認。最後可輸出文字或 TTS 語音，同時保存來源版本、工具回應、核准與錯誤紀錄。品質未過關時先停止或轉人工，不以追求低延遲掩蓋錯誤。

  • 鏈：ASR → 意圖／LLM → 權限化 RAG → Planner → MCP／API／A2A → 驗證 → 文字或語音。
  • 每一層分開測，才能知道錯在轉錄、檢索、生成、規劃或工具。

五、會議音訊：說話者、主題邊界與語意分群

會議處理不是只有 ASR。ASR 回答說了什麼；說話者分離或分段回答誰在何時說話；主題邊界偵測找出討論何時從一個議題轉到另一個議題；語意分群則把意思相近的發言或段落聚在一起。四者輸出與錯誤型態不同。

穩健流程會先保留時間戳與說話者，再依語意與停頓找候選邊界，最後將片段分群、命名主題並由人工抽查。不能只依換人就切主題，因為多人可能接續同一議題；也不能只靠關鍵字，因為同一概念可有不同說法。

  • 說話者切分看身分與聲學；主題邊界看語意轉折；語意分群看內容相似。
  • 主題切分與分群可搭配，但前者重時間順序，後者不必相鄰。

六、效能與營運：批次提高吞吐，不保證單筆更快

延遲是單一請求從送出到收到結果的時間；吞吐量是單位時間能處理多少工作。批次把多個請求一起運算，常能提高硬體利用率與整體吞吐、降低平均成本，但請求可能先等待湊批，因此不一定降低單一請求延遲，批次過大還可能增加記憶體壓力。

互動式服務通常重視首字時間、尾端延遲與尖峰穩定；離線摘要或大量嵌入可偏重吞吐。優化順序應是先用代表性資料確認 ASR、檢索、生成與動作品質，再量測瓶頸，最後依場景調整批次、快取、平行化與模型大小。

  • 批次通常利於吞吐，不是單請求延遲的萬用解。
  • 效能指標必須配場景：即時互動與離線處理的優先級不同。

七、8 分鐘誤區與提取練習

看到「最新且要引用」先想 RAG；「固定語氣」先試提示、模板與結構化輸出，再評估微調；「執行既定動作」看 API；「拆解多步目標」看 Planner；「統一工具接法」看 MCP；「專門代理互相委派」看 A2A。

閉書畫一次服務助手鏈，為每個箭頭標出輸入、輸出、權限與失敗處理；再用一句話分清會議中的 ASR、說話者、主題邊界與語意分群。最後回答：若整體變快但錯誤率上升，為什麼不算有效優化？

真正的端到端驗收還要保留代表性難例，例如口音、專有詞、跨段規則、無權限文件與工具逾時；只測順利案例，會高估系統在正式情境的可靠度。

  • 先品質後速度，不是永遠忽略速度，而是先守住可用底線。
  • 題目聲明：下方皆為概念原創單選，不是官方試題。

補強定位｜找得到、排得上、用得對，是不同關卡

RAG 通常先切分文件（Chunking），建立嵌入向量（Embedding）與索引，再檢索候選內容、必要時重新排序（Reranking），把相關且有權限的片段交給模型。向量檢索比對語意，關鍵字檢索比對字面；混合檢索可以互補。多向量表示可從不同角度代表同一文件，但並非任何情境都必然更好。

若條文已在候選結果中卻排名太後，問題可能在重排序，而不是一定要重訓模型或重建全部資料庫。若檢索不到，就回查切分、查詢、索引與版本；若檢索正確但回答亂說，就檢查指令、引用與生成。附來源仍須確認來源存在、版本正確、內容確實支持回答。

ReAct 將推理、工具行動與觀察交替進行；Prompt Chaining 將多個提示步驟串接，仍需驗證中間輸出，避免前錯後錯。Solution Graph 表示本次任務的步驟與依賴，Knowledge Graph 表示較長期的實體關係知識。多代理若共享狀態不一致，可能重複工作或使用舊結果；規劃需要角色、版本、交接條件與失敗處理。

  • API 是請求介面；Webhook 通常由事件發生後推送通知。對話上下文與長期記憶需有系統保存與取用設計，不是只靠一句『請記住』。

相近名詞，真正差在哪？

RAG ／ Fine-tuning

RAG 在推論時取外部證據；微調更新模型參數，偏行為與任務適配。

提示／模板 ／ Fine-tuning

兩者都可改善語氣格式；前者成本較低且易修改，微調不是唯一手段。

API ／ Planner

API 執行明確動作；Planner 拆解目標、排序並選擇動作。

MCP ／ A2A

MCP 偏 AI 與工具／資源的協定；A2A 偏代理與代理的任務協作。

同步 A2A ／ 非同步 A2A

前者等待當次回應；後者可先回任務狀態，完成後再更新或交付。

說話者分離 ／ 主題邊界／語意分群

前者判斷誰何時說；後兩者處理議題轉折與內容相似性。

吞吐量 ／ 單請求延遲

批次常提高前者，但等待湊批可能不降、甚至增加後者。

換個產業，還能用同一個邏輯嗎？

中性服務助手接受語音提問，回答最新版規範，並在使用者確認後查詢案件或建立申請。

先以 ASR 轉錄及標記低信心；RAG 先做身分與文件權限過濾並附版本引用；Planner 只在多步任務拆解；MCP 可統一工具介面，API 執行動作，A2A 可把專門任務委派給 Remote Agent。改變外部狀態前需確認，失敗要回退或轉人工。

物流中心要把每日大量配送異常紀錄整理成摘要，並把需處理者寫入既有工單系統。

規則頻繁更新且需追溯，適合 RAG；固定欄位可先用模板或結構化輸出，不急著微調；離線大量摘要可用批次提高吞吐，寫入工單則用受控 API，不能因批次量大就假設每筆延遲更低。

教育機構要把長時間研討會轉成逐字稿、分辨發言者、切出議題並彙整相似觀點。

ASR 轉文字；說話者處理誰在何時發言；主題邊界沿時間找議題轉折；語意分群可把不相鄰但意思相近的段落聚合。先抽查專有詞、數字與邊界品質，再優化處理速度。

這些是要避開的錯誤說法

  • RAG 會自動保證答案正確，因此不用測檢索與引用。
  • 先把所有文件檢索出來，再由模型自行決定哪些內容有權看。
  • 要固定語氣只有 Fine-tuning 一種方法。
  • 微調後模型會自動知道每天更新的外部規範並逐句附來源。
  • 能呼叫 API 就等於系統具有 Planner 與完整代理能力。
  • MCP 與 A2A 都有協定，所以用途完全相同。
  • A2A 一定同步；Client Agent 發起後 Remote Agent 不可延後回報。
  • 會議中一換說話者就一定代表主題改變。
  • 語意分群只能處理相鄰片段。
  • 批次越大，單一請求延遲一定越低。
  • 先把延遲降到最低，品質與權限可等上線後再補。

以上是誤區，不是正確結論；請用前面的對照說明它為什麼不成立。
