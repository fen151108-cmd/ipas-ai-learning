DAY 7 / 7 · 兩科整合驗收

從需求到擴散：導入、測試、漂移與第二週驗收

先證明問題值得解、方案做得到，再用分層測試與受控試點上線；監控要分清資料、概念與欄位變化，事件由人負責，擴散依證據而非熱度。

建議 45–60 分鐘：先框架與必讀，再對照與案例，最後 8 題練習。選讀區可留到第二週。完成閱讀不等於已掌握。

直接練習回到大框架

今天為什麼要學？

把前六天名詞接回完整企業AI生命週期：先定需求與KPI，再查資料與資源，逐步POC、MVP、試點、部署、監控與擴散。

  • 能依需求、KPI、資料資源可行性、POC或MVP、試點、部署、監控與擴散排列導入決策
  • 能分辨測試層級、批次處理的吞吐與延遲，以及三種漂移和過擬合
  • 能用未看過的計時題分類錯因、補最弱概念並再測，不把八題誤當正式模考

一、框架：一條主線收束兩科

完整主線是需求與現況、KPI、資料與資源可行性、方案選擇、POC或MVP、受控試點、正式部署、監控改善、價值擴散。科目一提供資料、模型、指標、隱私與安全基礎；科目二把它們變成導入判斷。第一步不是買熱門工具，而是把痛點改寫成可量測結果，並設定品質與風險護欄。

  • 高價值但資料不合法或無人覆核，仍不能直接做
  • 易做但無業務價值的題目，不因技術新穎就優先

二、白話：POC、MVP、試點與部署

POC以有限資料與事前門檻驗證關鍵假設；MVP是能讓目標使用者完成核心任務的最小可用產品，開始收集真實使用回饋。試點把方案放入受控真實流程，檢驗角色、整合與維運；正式部署則要求長期權限、監控、版本、事件與退場機制。前一階段成功只表示值得進下一關，不代表全面擴散。

  • POC偏向可行性證據，MVP偏向最小可用價值
  • 部署前要能回退、轉人工與追溯版本

三、工具與測試：低門檻不等於免工程

No Code／Low Code可快速製作表單、工作流與原型，但仍須做權限、資料、例外與效能測試。自動化是讓規則化步驟依條件執行；API是系統間明確交換請求與回應的介面；服務虛擬化用模擬相依服務，讓外部系統尚未完成或不宜直接呼叫時仍可測試。單元測單一元件，整合測元件介接，端到端測完整使用流程。

  • 視覺化開發加快交付，不會自動消除供應商鎖定或Shadow IT
  • 測試越接近真實流程，範圍更完整但成本與診斷難度通常更高

四、效能與漂移：先看變的是哪一層

批次處理（Batch）把多筆工作集中執行，常有利於總吞吐量；吞吐量是單位時間完成多少工作，延遲是單一請求等多久，兩者不能互換。Data Drift是輸入分布變化；Concept Drift是輸入與正確結果的關係改變；Schema Drift是欄位名稱、型別或結構改變。過擬合則是模型把訓練資料細節與雜訊學得太深，未見資料表現差，不是上線後環境變化。監控時也要持續追蹤成本變化。

  • 漂移是調查訊號，不等於可跳過驗證自動重訓上線
  • 監控應同看系統、品質、資料、風險與業務KPI

五、事件處置：AI不承擔責任

發現外洩、越權或品質驟降時，依序偵測、分級、止血或回滾、保存證據、通報、找根因、修正測試、受控恢復、事後改善。可先停自動動作、切回人工或舊版，避免影響擴大。業務、系統、資料、資安與審查角色要事前分工；供應商或模型可以提供功能，但批准、處置與對外責任仍由組織中的人承擔。

  • 人工覆核必須有資訊、時間、能力與改判權
  • 保留提示、模型、知識庫、資料、流程規則與護欄版本

六、完整案例：三個產業走同一條線

醫療摘要先以臨床一致與漏失風險為護欄，小範圍POC後才進受控試點。銀行文件助理先確認資料權限，以模擬API測整合，再由人核准對外動作。零售補貨模型先比較現況KPI；若新品使輸入分布改變，調查Data Drift，若促銷後相同特徵對需求的關係改變，調查Concept Drift。三者都要在相似新場景再試點，不能直接複製。

  • 擴散的是驗證方法、控制與監控框架，不是硬套同一模型
  • 案例與題目皆為中性原創材料，不是官方原題或押題，須依證據判斷

七、第二週遷移：計時、分類、補弱、再測

第二週先選未看過的兩科混合題，在固定時間內閉卷作答；記錄每題耗時與信心，再把錯誤分成知識缺口、情境映射、題幹陷阱、提取失敗或粗心。只補最弱的一至兩類，回看概念地圖、做教回與少量變式題，隔天用另一組未看題再測。可自訂七成為個人練習門檻，但不是官方及格規則；本課八題只是單元驗收，不是假裝正式模考。

  • 錯題要寫考點、錯因、正確判斷與其餘選項錯在哪
  • 再測若仍錯，回到概念與案例，不用大量同題型掩蓋缺口，並記錄下一次檢驗條件

必讀補強｜TCO、ROI 與 Token Economics：值得做不等於做得出

TCO 是整段使用期間的總體擁有成本，包含開發整合、模型或 API、硬體雲端、維運、資料整理、人員訓練與退場移轉等，不只購買價格。ROI 比較同一期間的效益與投入；常用形式為（效益－成本）／成本。不能把節省時間直接當成現金收益，也不能只說準確率提高就代表投資一定划算。

Token Economics 看輸入、輸出、可計費的推理或其他 Token 用量與各自單價，實際以服務計價規則為準；中文字數並不固定等於 Token 數。假設每月只有一百萬個輸出 Token、輸出每百萬 Token 二十元，則這部分成本為二十元，尚未包含輸入與其他費用。若同期間效益十五萬元、總成本十萬元，依上述公式 ROI 為百分之五十；範例是假設教學數值，不是服務報價。

No Code 降低手寫程式門檻，Low Code 保留少量程式擴充；AutoML 著重自動處理模型搜尋、特徵或超參數流程，Vibe Coding 以自然語言反覆生成修改程式。都不能免除需求、測試、資安與維護。平台選型要查 API、資料匯出、客製能力、效能、稽核與供應商鎖定；企業開放部門自行開發時，也要管理 Shadow IT。

  • 生成式 AI 品質驗收不只看平均分數，還要測重大資訊是否漏失、引用是否支持回答、工具是否越權；擴大規模前先訂成功門檻與停止條件。

相近名詞，真正差在哪？

POC ／ MVP

POC驗證關鍵假設是否可行；MVP以最少功能讓目標使用者完成核心任務並收集回饋。

單元測試 ／ 整合／端到端測試

單元測單一元件；整合測介接；端到端從使用者入口走完整流程。

吞吐量 ／ 延遲

吞吐量看單位時間完成量；延遲看單一請求等待時間，批次化可能提高前者卻拉長後者。

Data／Concept／Schema Drift ／ 過擬合

三種漂移分別是輸入分布、輸入與目標關係、欄位結構改變；過擬合是訓練時記住細節而泛化不佳。

換個產業，還能用同一個邏輯嗎？

醫療團隊規劃門診摘要草稿。

先定臨床一致、漏失風險與人工覆核，再檢查資料合法性；POC達門檻後仍只在受控流程試點，監控修正率與事件。

銀行要讓文件助理查規範並建立申請草稿。

以最小權限限制資料與工具，用服務虛擬化模擬尚未開放的核心API，依單元、整合、端到端逐層測試，高影響送出由人核准。

零售商用模型預測各店補貨。

需求與KPI先對齊缺貨率及庫存成本；上線後分辨新品造成的Data Drift、促銷規則改變造成的Concept Drift及欄位改名的Schema Drift，再受控修正。

這些是要避開的錯誤說法

  • 先買工具，再反向尋找需求與KPI。
  • POC或MVP成功就直接全面部署，省略試點與治理。
  • No Code／Low Code不寫或少寫程式，所以不需要測試與資安審查。
  • 批次處理一定同時提高吞吐量並降低每筆延遲。
  • 看到表現下降就一律稱資料漂移，或直接自動重訓上線。
  • 把八題單元驗收或自訂七成門檻宣稱為正式模考與官方規則。

以上是誤區，不是正確結論；請用前面的對照說明它為什麼不成立。

遮住筆記，試著教回

  • 用一個陌生企業情境，依需求、KPI、資料資源、POC或MVP、試點、部署、監控、擴散說完整導入路徑。
  • 不看表格比較Data Drift、Concept Drift、Schema Drift與過擬合，各舉一個訊號及第一個處置動作。
