No Code 與 Low Code

No Code 用視覺化元件完成常見需求，Low Code 以視覺化為主、用少量程式碼處理整合與客製；少寫程式，不等於沒有設計、測試與治理。

今天不以「有沒有程式碼」二分好壞，而是從建構方式、主要使用者、需求複雜度與客製彈性判斷適用情境。

TWO DEVELOPMENT POSTURES

二、正確定義：共同降低門檻，但保留的程式碼彈性不同

NO CODE用設定組合常見需求

以視覺化介面、拖放元件、模板與規則設定為主，讓使用者不必直接撰寫程式碼即可建立應用。[2]

適合：快速原型、簡單流程、小型內部工具。
LOW CODE視覺化為主，程式碼補彈性

沿用視覺化建構，同時允許少量程式碼處理深度整合、特殊介面與複雜邏輯。[2]

適合：客製需求、既有系統整合、較複雜應用。

官方學習指引將 No Code 描述為透過視覺化介面與拖放操作完成應用；Low Code 則結合視覺化工具與程式碼擴充，以保留較高的整合與客製彈性。[2]

共同起點需求與流程先定義要解決什麼問題
→
共同手段視覺化建構元件、模板、規則、連接器
→
分歧點是否需程式碼擴充？標準需求偏 No Code；複雜整合偏 Low Code
→
共同責任測試、部署與維護快速建構不會消除治理
COMPARE BY FOUR AXES

三、比較表：不要只看「程式碼多或少」

判斷面向No CodeLow Code題目判斷重點
建構方式拖放、模板、規則設定視覺化＋少量程式碼是否明確需要自訂程式
主要使用者非技術背景或業務使用者也可參與具技術基礎者或業務與技術混合團隊不是用職稱絕對分類
適合需求標準、簡單、快速驗證複雜邏輯、特殊介接、較高客製需求複雜度比工具名稱重要
速度與門檻通常較快、入門門檻較低仍比全手寫開發減少重複工作快不等於不用設計與測試
彈性與維護受平台元件與規則限制較多彈性較高，但需管理自訂程式碼兩者都可能有平台依賴
較偏 No Code標準化、速度、低門檻 需求與能力配對 較偏 Low Code整合、客製、複雜邏輯

官方指引把目標使用者與技術需求、功能與擴展性、安全合規、成本效益及技術支援列為平台評估面向；因此選型不能只比較開發速度。[2]

WHAT THE PLATFORM HIDES

四、視覺化不等於沒有系統：仍有五個建構層

01 · UI介面元件表單、按鈕、清單與畫面配置
02 · DATA資料結構欄位、資料表、驗證與關聯
03 · LOGIC規則流程條件、觸發、分支與例外
04 · INTEGRATION連接器與 API資料來源、外部系統與權限
05 · OPERATE部署與維護測試、版本、監控與修正

平台替使用者抽象掉部分底層實作，卻沒有讓需求、資料、流程、權限與維運消失。[2] 考題若把「不寫程式」推論成「不需任何技術判斷」，通常就是把抽象化誤認成責任消失。

ONE SCENARIO THROUGHOUT

五、貫穿情境：家庭共享用品補充工具

一個家庭想記錄清潔用品、衛生紙與常用物品的剩餘數量，低於門檻時提醒補充。這是原創中性教學情境，不涉及真實家庭或店家資料。

共同需求登記品項與數量，低於門檻便提醒
  • 輸入：品項、數量、補充門檻
  • 規則：數量低於門檻
  • 輸出：補充提醒與待辦清單
NO CODE PATH標準流程先驗證

拖入表單與清單元件，設定條件式通知。需求單純，平台既有功能足夠。

價值：快速建立與試用。
LOW CODE PATH複雜需求再擴充

若要串接不同店家的商品介面、自訂折扣規則或多層權限，保留視覺化流程，再用少量程式碼補上。

價值：增加整合與客製彈性。
選型關鍵不是先選平台再硬塞需求，而是先看使用者能力、流程複雜度、整合需求、風險與後續維護。若需求持續成長，也要重新評估是否仍適合原本的開發方式。
DON’T COLLAPSE THE CONCEPTS

六、六組容易混淆的差異

官方指引明確提醒，No Code／Low Code 能降低門檻與縮短開發時間，但不能完全消除專業技術需求，也仍須面對整合、安全、隱私與驗證問題。[2]

No Code vs. 無需技術判斷不寫程式 ≠ 不用懂需求

欄位、流程、權限、例外與測試仍要設計。

Low Code vs. 傳統全手寫少量擴充 ≠ 所有部分自行開發

Low Code 仍以平台視覺化能力為主要骨架。

No Code vs. AI開發方式 ≠ 系統能力

No Code 可以不含 AI；AI 功能也能以傳統程式開發。

快速原型 vs. 正式上線做得出來 ≠ 可安全營運

正式使用仍要驗證資料、權限、可靠性與維護方式。

低門檻 vs. 無限制容易開始 ≠ 可以無限客製

平台元件、連接器、效能與定價都可能形成邊界。

工具效率 vs. 人員取代減少重複開發 ≠ 完全不需專業人員

複雜整合、安全與治理仍可能需要專業能力。

EXAM TRAPS

七、iPAS 題目判斷訊號

  1. 「拖放、模板、無需直接撰寫程式碼」：先想到 No Code。[2]
  2. 「視覺化工具＋少量程式碼擴充」：先想到 Low Code。[2]
  3. 「複雜邏輯、既有系統整合、高度客製」：通常較偏 Low Code，而非硬說 No Code 可無限處理。[2]
  4. 「快速原型、簡單工作流程、非技術背景使用者」：通常較偏 No Code。[2]
  5. 「完全取代專業開發者／完全不需技術知識」：絕對化敘述，優先排除。
  6. 「平台內建 AI，所以 No Code 等於 AI」：錯；兩者分屬開發方式與系統能力。
  7. 「開發快，所以不需測試、權限與治理」：錯；實作抽象化不會讓營運責任消失。
EXAM METHOD

八、四問辨認法：需求先於平台名稱

01建構：只需拖放與設定，還是明確需要程式碼擴充？
02複雜度：標準簡單流程，還是特殊邏輯與深度整合？
03層級：題目在談開發方式，還是在談 AI 的能力？
04陷阱：是否出現「完全、無限、必然取代、不需測試」等絕對字眼？
