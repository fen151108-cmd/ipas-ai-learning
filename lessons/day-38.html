AI 代理與工具協作

API Calling 是呼叫能力；MCP 標準化代理與工具／資料的連接；A2A 處理代理間協作；Agentic AI 再把目標、規劃、行動、回饋與控制串成循環。

分清 MCP、A2A、Agentic AI、Solution Graph 與 API Calling，設計可控、可追蹤的多工具協作。

Day 38約 45–65 分鐘名詞白話＋完整案例＋6 題原創情境題＋Podcast
MODULE 09｜反向補強

先定位：由名詞缺口回頭補齊概念

RAG 讓跨部門服務問答助手能引用最新規範，但使用者仍要手動建立工單、查詢進度與安排回電。團隊希望讓助手在授權範圍內完成跨系統任務，同時避免「模型一句話就能任意操作」。

來源與題目聲明

本模組由官方公開學習資源、評鑑範圍與考古題暴露的名詞缺口反向補強；本站重新建立中性案例、比較與理解題。所有題目皆為原創，不是官方原題，也不宣稱預測實際考題。

本課名詞API 呼叫、模型脈絡協定、代理對代理協定、代理式 AI、解決方案圖
01｜白話名詞

先理解「它解決什麼問題」

API Calling

API 呼叫

依既定介面送出參數並接收結果，例如建立工單。它是直接整合方式，不等於自主規劃。

MCP

模型脈絡協定

用共同協定描述與連接工具、資源及提示，降低每個 AI 應用各自客製連接的成本；仍需權限與安全設計。

A2A

代理對代理協定

讓不同代理發現彼此能力、委派任務並交換狀態或成果；重點是代理間協作，不是工具接頭。

Agentic AI

代理式 AI

圍繞目標進行規劃、選工具、執行、觀察與修正的系統；自主程度愈高，控制、停止與稽核愈重要。

Solution Graph

解決方案圖

把業務目標、子問題、依賴、資料、工具、代理與控制畫成關係圖，先釐清整體再選技術；不是特定單一產品。

03｜易混淆表

不要只背名詞，要看差異軸

容易混淆真正差異判斷方式
API Calling vs. Agentic AIAPI Calling 是一次介面互動；Agentic AI 會依目標規劃多步並根據結果調整。看到固定步驟可直接 API；看到目標導向循環才是代理式。
MCP vs. A2AMCP 偏 AI 應用連工具／資源；A2A 偏代理與代理交換任務。一句話：MCP 接工具，A2A 接代理；兩者可同時使用。
Solution Graph vs. 工作流Solution Graph 描述問題、能力與依賴；工作流是可執行步驟與條件。圖不是執行器，但可協助找出缺口與控制點。
代理 vs. 聊天機器人聊天可只回覆文字；代理還會選工具、改變外部狀態或持續追蹤任務。是否「採取動作」與「閉環回饋」是重要線索。
自主 vs. 無人監督自主提高不代表必須移除人。高影響、不可逆、花費或對外動作通常要人工核准。
04｜考題判斷線索

先圈情境訊號，再選概念

01

固定參數、單次呼叫

先想到 API Calling，不必把所有整合都稱為代理。

02

多個工具介面希望一致

工具／資源發現與呼叫標準化，想到 MCP。

03

專門代理互相委派

能力發現、任務狀態與成果交換，想到 A2A。

04

目標—規劃—行動—觀察—修正

這是 Agentic AI 的典型閉環。

05

先畫問題與依賴

看到目標、資料、工具、代理、控制關係，想到 Solution Graph。

06

動作會扣款、送出或改資料

權限、參數驗證、人工確認、冪等與回退都比「更聰明」重要。

作答原則

先判斷題目要解決的問題、資料與動作發生在哪一層，再排除只因名詞相似的選項。選「最直接符合線索」者，不把新技術自動視為最佳答案。

05｜案例決策紀錄

能力、控制與驗證必須一起設計

最終流程由協調代理提出計畫，但建立工單與預約回電都先做權限檢查、參數驗證與人工確認；工具只回傳必要資料，代理間傳遞任務狀態與可驗證結果。失敗時可重試、回退或轉人工，所有動作寫入稽核紀錄。

連續案例原則每一日都沿用同一個跨部門服務問答助手；新增能力不會抹除前一日的資料治理、人工覆核、版本、引用、權限與監控責任。
RETRIEVAL PRACTICE

原創情境理解題

先作答再看解析。以下 6 題由本站依概念缺口自行設計，不是官方原題，也不重製任何考題。

1. 助手收到已確認的工單欄位，只需呼叫既有服務建立一筆紀錄。最簡單合理的整合是？
2. 團隊有文件搜尋、工單、行事曆三種工具，希望不同 AI 應用用一致方式發現與呼叫。較符合什麼？
3. 「規範代理」需把查證結果交給「排程代理」，並持續回報任務狀態。較符合什麼？
4. 協調代理會依目標拆步驟、呼叫工具、讀取結果並在失敗時改計畫。這最接近？
5. 團隊還未決定用幾個代理，先把目標、子任務、資料依賴、工具、人工核准點畫成關係圖。這是？
6. 代理準備替使用者送出預約，但時間與聯絡方式尚未再次確認。最適當處置是？
